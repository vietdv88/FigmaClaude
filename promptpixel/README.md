# PromptPixel

PromptPixel is a Figma plugin that turns prompts into interfaces constrained by your design rules and published component library.

## Current foundation

- Simple BYOK setup with provider and API key; model and endpoint overrides live under Advanced. The "Model override" field is a searchable combo box (native `<input list>`): hit "Tải danh sách" to fetch the live model list straight from that provider's API (using the key you've typed or already saved) and pick from it, instead of guessing/typing a model id that may be outdated — provider default model ids drift over time and can 404 once retired. Each provider's list is already scoped to that provider only (no cross-provider mixing); non-chat entries (embeddings, audio, image generation, moderation, legacy completion-only models) are filtered out by name pattern (or, for Gemini, by its own `supportedGenerationMethods` flag, and for OpenRouter, by its `architecture.output_modalities` metadata) so only models actually usable for JSON UIPlan generation show up.
- API keys persist locally in Figma `clientStorage` until the user removes them, clears local browser data, or changes the plugin ID. Keys are never stored in a Figma document, and never leave the plugin's main thread (the UI iframe only ever sees whether a key is saved, never its value).
- Design rules split by screen type (General, Overview/Dashboard, List, Detail) so common layout conventions aren't easy to forget, stored locally for the plugin. Each field starts pre-filled with a sensible sample rule set (spacing, CTA usage, list/detail layout conventions) — edit or clear whatever doesn't apply.
- Load enabled libraries from the current design file through Figma's available library variable collections (only libraries that publish at least one Variable Collection are discoverable — see limitation below). Each library can carry its own description explaining what it's for, which is fed to the AI alongside the component catalog.
- Library Profiles let users explicitly enable the design-system libraries AI may use.
- Component catalogs and semantic matching stay behind the scenes instead of requiring users to map components one by one. On scan, every component gets an auto-filled `aiDescription`: a small built-in dictionary recognizes common UI element names (Button, Input, Checkbox, Card, Sidebar, Modal, ...) and fills in a fuller Vietnamese description of what it's typically used for; anything not recognized falls back to a plain word-split of the component's Figma name (e.g. `NavBar/ItemActive` → "Nav Bar Item Active"), and the component's own Figma "Description" field (if set) always takes priority over both. The description shows as a small preview line under the component's name in the list. For non-icon components, a "Sửa" button lets you override the description manually when the auto-derived guess isn't good enough; icon components (page "Icons") skip that editor entirely and just show their auto-derived description read-only, since the whole point of the Icons pool is that it doesn't need per-icon curation.
- Shared TypeScript schema for the AI-generated `UIPlan`, including plain Auto Layout container nodes (`layout`) alongside component-instance nodes (`componentId`).
- For OpenAI/OpenRouter, the one remaining AI call that returns structured data (the leaf-mapping call — see below) is sent with a real JSON Schema built per-request from the currently enabled catalog (`src/schema.ts`, `buildLeafDecisionsJsonSchema`) via `response_format: json_schema`, with genuine `enum` constraints for componentId/text-style names — not just a prose description of the shape. This is schema-guided generation, not OpenAI's fully-closed "strict" mode (which can't express `properties`, an inherently open-ended dictionary), but it meaningfully cuts down on structurally-invalid output at the model level instead of only catching it after the fact.
- Gemini gets the same treatment through its own schema dialect (`generationConfig.responseSchema`, `buildGeminiLeafDecisionsSchema`) — uppercase `type` values, no `$ref`. Since the leaf-mapping response is a FLAT array (never a nested tree — see below), there's no depth to unroll and no risk of an enum list multiplying across nesting levels the way an earlier, tree-shaped schema did, so the full componentId enum can safely appear here for Gemini too. Anthropic and custom/OpenAI-compatible endpoints still rely on the prose-described schema in the system prompt for this release.
- A "Generate" tab sends a free-text screen description (and/or an image export of the currently-selected canvas node, analyzed as a layout reference) to the active provider, validates the JSON response against the enabled component catalog, and builds the result (frame + component instances + properties + Auto Layout) directly on the current page.
- Two fixed generation workflows are baked into the plugin itself, not left to per-project Rules text, so behavior is consistent for every user:
  - Generation goes through an HTML intermediate step, with structure built DETERMINISTICALLY rather than trusted to an AI call — asking a single call to reproduce a whole screen's structure directly as the catalog-grounded UIPlan JSON (including two earlier architectures: a monolithic call, then a per-region-call one) reliably collapsed into near-empty output, invented componentId values, or oversized requests that failed outright, no matter how the prompt or chunking was structured. **Step 1** asks the AI to sketch the *entire* screen as plain HTML with inline CSS — no component catalog involved at all (`buildHtmlWireframePrompt`) — playing to a format the model is far more fluent and thorough in than our bespoke JSON schema; every structure/content decision (which regions exist, their arrangement, every button/field/row/label and its real literal text) gets made here, unconstrained. It retries once if the result comes back with suspiciously few HTML tags, and is shown in the Generate tab immediately (`GENERATE_HTML_WIREFRAME`) so it's inspectable before conversion even starts. **Step 2** parses that HTML with the UI iframe's real `DOMParser` (the plugin's main thread has no DOM of its own) and walks the resulting tree in `code.ts` to build the UIPlan tree structure directly — every container element becomes a `layout` node, every leaf becomes a placeholder seeded with its own literal text as a safe fallback. No AI call is ever asked to reproduce this structure, so it can't drop, condense, or invalidate it. **Step 3** draws that ENTIRE structure onto the canvas immediately, before any AI component-mapping call even runs — every placeholder still as its safe deterministic fallback (real text, plain layout frames). This is the actual, visible result if the next step's AI call did nothing whatsoever — never blank, never dependent on that call succeeding. **Step 4** is a flat AI call over the leaf placeholders (`buildLeafMappingSystemPrompt`) — for each one, decide the best-fitting catalog component (or leave the safe text fallback); only the ids it actually upgrades then get patched into the frame step 3 already drew, found by their own stable id (every node's Figma layer name is set to its own plan-node id at creation time), never by fragile sibling position — the same reason an earlier "clone a similar previous frame and patch by index" attempt reliably deleted more than it reused (see below) doesn't apply here: this patches the SAME frame that was just built from the SAME plan, so every id is guaranteed to exist exactly once. Even total failure of this call just means every element keeps the safe fallback step 3 already drew — never blank, never reverted. Colors need no AI call at all: a library scan now also captures each Color Style's own actual solid color (0-1 RGB, straight from Figma), so a container's background/border color is resolved the moment it's read off the wireframe, by real RGB distance to the closest loaded Color Style (`matchNearestPaintStyle`) — a purely deterministic lookup, always reproducible, with no LLM guessing involved. **This only works for a library scanned after this change** — re-scan (Libraries tab → "Nạp lại...") to pick up existing Color Styles' actual colors; until then they have no captured color to match against, same as before. This applies uniformly whether or not a reference image is attached — for a screenshot recreation, an exhaustive text description of the image is extracted once up front (`buildImageDescriptionPrompt`) and fed into step 1.
  - Parsing HTML into the tree (step 2) also handles "mixed content" correctly — an element with both a child element AND its own bare trailing text (e.g. `<li><span class="icon">🔧</span> Ứng dụng AMIS</li>`, extremely common in generated wireframes for icon+label pairs) keeps that trailing text as an extra leaf instead of silently losing it, which an earlier version (walking only element children) did; its own position is measured via a DOM Range (see below), since it has no element of its own to measure directly.
  - Every node is positioned ABSOLUTELY — its exact rendered box (`getBoundingClientRect`, relative to its own parent) is captured while parsing and carried straight through as that node's x/y/width/height in Figma, rather than reconstructed via Figma Auto Layout (direction/wrap/align/padding/gap/stretch-vs-hug). An earlier version tried the latter, mapping CSS properties onto Figma Auto Layout's closest equivalents one at a time (`display:flex` defaulting to row, `justify-content`/`align-items` onto `primaryAxisAlignItems`/`counterAxisAlignItems`, `display:grid` approximated as a wrapping row) — but CSS's box model and Figma's Auto Layout don't correspond 1:1, so each fix for one property/pattern kept exposing the next (misaligned rows, a child forced to stretch past its own content's natural height and overflowing into its neighbor, grid columns collapsing into a single column) — a structurally unbounded chase. Absolute positioning sidesteps needing to close that gap at all: since a DOMParser-created tree is detached and never actually renders/cascades CSS or computes layout, the wireframe HTML is injected into a hidden Shadow DOM host (synchronous, no iframe/timing to get wrong; its `<style>` block stays fully scoped to that shadow tree instead of leaking into/colliding with the plugin UI's own styles) sized to the actual target canvas, so the real browser lays it out exactly as it would for that canvas before anything is measured off it. Any container whose direct children form a clean, evenly-spaced single row or column gets promoted to a REAL Figma Auto Layout frame anyway (`detectAutoLayoutPattern`) — not by reading CSS at all, but by measuring the gap/padding directly from those children's own already-correct absolute positions and setting `layoutMode`/padding/`itemSpacing` to match, so it starts out visually identical to the absolute layout but is reflow/resize-friendly afterward. This also applies to the top-level regions themselves (header, sidebar+content, ...) against the root screen frame. A container that doesn't cleanly resolve to one direction/gap (overlapping children, a wrapped/grid arrangement, irregular spacing) is left as plain absolute positioning instead, since forcing a single gap value onto it would visually misplace it — this is the residual trade-off: most simple rows/columns become real, editable Auto Layout, but a wrapped card grid (for example) stays a fixed snapshot.
  - Any container whose total leaf-descendant count is within `BIG_WHOLE_MAX_LEAVES` (30) — from a small "leaf-like" one, e.g. an icon next to a label (a nav item, a status badge, an icon button), up to a bigger composite region (a header bar, a sidebar nav block, a card) — is ALSO offered to the leaf-mapping call as a whole, alongside its own children's individual candidacy, since a design system commonly has exactly one real component for a pattern like that which a strictly-leaf-only view of the tree could never reach. The AI is explicitly told this is opt-in and to skip it whenever a bigger container isn't a genuinely strong structural + content match — the individual pieces inside are already offered as their own candidates too, and the container itself already has a correct deterministic fallback either way, so a skip never loses anything.
  - A standalone icon leaf (a lone glyph/emoji character, an `<svg>`, a bare `.icon` span with no other content) never stays a literal unicode-character text fallback when the catalog has one — the leaf-mapping prompt explicitly instructs finding a generic icon-holder component (typically named "Icon"/"Swap Icon"/"Icon Wrapper", exposing one INSTANCE_SWAP property) and setting its icon-swap property to the closest semantic match from the icon catalog (by the element's own text/attrs/ancestry context), the same way a component's own icon-swap property gets filled elsewhere. `isIconComponent` (deciding which scanned components count as "raw icons," never directly assignable) now also excludes anything that itself exposes an INSTANCE_SWAP property of its own — an icon-holder wrapper like "Icon Swap" commonly lives on the same "Icons" page as the individual icon glyphs it swaps between, and page name alone would otherwise misclassify it as one of those raw icons, contradictorily telling the model it's both an available component AND forbidden to assign directly.
  - An `<svg>` (a real vector icon graphic, not a unicode glyph — some wireframes use one style, some the other) is treated as ONE atomic leaf — its internal `<path>`/`<circle>`/... markup is never walked into at all, since those have no text of their own and aren't a "meaningful empty leaf" tag either; recursing into them would decompose the icon into a container wrapping content that then gets silently dropped entirely, leaving an invisible gap exactly where the icon should be. The "leaf-like container" whole-promotion check (nav item/status badge/icon button) is also depth-independent (counts total leaf descendants across the whole subtree, not just direct children) for the same reason — an SVG-based icon commonly sits one level deeper (wrapped in its own `<div class="icon">`) than the plain-glyph equivalent (a bare `<span class="icon">`), which a shallow one-level check would otherwise miss.
  - Borders are handled the same deterministic way as fills — any container whose CSS specified a visible border color gets the closest loaded Color Style by the same RGB-distance match. When nothing loaded is close enough (or no Color Style has a captured color to match against at all, e.g. before a library re-scan), the wireframe's own literal CSS color is applied directly as a plain solid fill/stroke instead of leaving the element with no color at all — a deliberate fallback, since a color that isn't tied to a real design-system style is still preferable to no color showing up. The Generate tab warns explicitly when this fallback is in play so it's clear the result isn't using real Color Styles yet. A container whose CSS specified any `box-shadow` gets a small fixed drop-shadow effect instead of a precise reproduction — Figma has no "loaded Effect Style" registry this plugin scans the way it does Paint/Text styles, so this is a deliberately generic "elevation" look rather than an attempt to match the exact shadow value. `border-radius` maps directly onto Figma's own `cornerRadius`.
  - A large/detailed screen's HTML can be genuinely long enough to hit an output-length cap mid-response, coming back with an unclosed tag or a container that never got its matching close — every provider call now sets an explicit `max_tokens`/`maxOutputTokens` (16384) so none of them silently falls back to a much smaller provider-side default (common for self-hosted/OpenAI-compatible endpoints when the field is omitted entirely). `requestHtmlWireframe` also checks the returned HTML's own tag balance (`isLikelyTruncatedHtml` — ends mid-tag, or some tag opened without ever being closed) as a second, independent signal from the existing "suspiciously few tags" sparse check, retries once with a message asking the model to finish every open tag (trimming content if it must) rather than stopping mid-structure, and — if it's still truncated after that — surfaces a warning in the Generate tab instead of silently shipping a half-built screen.
  - The root screen frame's own background comes from the wireframe's own `body { background: ... }` rule (the whole screen's background color is extremely commonly set there) — resolved the same deterministic way as any other container's fill. Setting `shadow.innerHTML` to a full document string never actually creates a literal `<body>` element (browsers silently drop a `<body>` start tag encountered mid-fragment-parse, only inserting its children), so that rule would otherwise match nothing at all; a real `<body>` element is created explicitly (via a separate, detached `DOMParser` pass to extract its actual inner HTML/`<style>` content) specifically so it does.
  - A container with no detected CSS background gets its fill explicitly cleared (`fills = []`) rather than left alone — a freshly created Figma frame otherwise keeps its own default opaque white fill, which then hides whatever's actually meant to show through from behind it (a gray page background, a parent's own color), making nearly everything look solid white regardless of the wireframe's real colors.
  - Text color is resolved the same deterministic way as a container's background/border — an element's own resolved `color` (an inherited CSS property, so already accounting for wherever up the ancestor chain it was actually declared) maps onto the closest loaded Color Style, or the literal CSS color directly as a fallback, applied to the text node's own `fills` (Figma has no separate "font color" property — a text node's glyph color IS its fill, same mechanism a shape's background uses).
  - A text node longer than ~40 characters (body copy) keeps its measured WIDTH (so it keeps wrapping at roughly the same point) but auto-sizes its height, rather than being fixed to the exact measured box — Figma's own font metrics can differ slightly from whatever font the browser actually substituted, and a fixed height would silently clip content instead of growing to fit it. A shorter label/caption/button/badge auto-sizes on BOTH axes (hugs its own single-line content) so it can never wrap or get clipped for the same reason, even if that renders it a little wider/narrower than originally measured.
  - The user's own free-text request is always wrapped with a short framing note before being sent (`buildUserPrompt`) making clear it's content requirements, not response-format instructions — a request phrased like a brief to a human designer (asking for an explanation, "quick tips", a prose "structural tree") was otherwise pulling the model toward writing an actual explanatory answer, or a technically-valid but essentially empty plan, instead of populating real content.
  - Every generation always builds a brand-new frame at the standard screen size (an earlier version tried reusing/patching a similar previously-generated frame first, but the HTML-parse-driven pipeline above produces a differently-shaped tree on every single run, which made that index-based patching reliably remove far more of the freshly-built content than it reused).
  - Every newly generated or cloned frame is placed beside existing top-level frames on the page (never overlapping them).
  - When something needs no matching component at any granularity, or is ambiguous enough that the AI has to make a judgment call, the `UIPlan` can carry optional `missingComponents`/`assumptions` note arrays instead of silently approximating or guessing with no record — these show up in the Generate tab's warnings list ("Thiếu component: ..." / "AI tự giả định: ...") alongside the usual per-node warnings.
  - Configured Design Rules always take precedence over the free-text request when the two conflict.
  - After the frame is built, if a reference screenshot was used PromptPixel also asks the AI to compare the rendered result against that original screenshot and shows the notes (match or a list of differences) in the Generate tab. This is purely informational — nothing is auto-modified on the canvas from it. (An earlier version tried auto-"fixing" a mismatch by asking for a whole revised UIPlan JSON in one shot and patching it over the already-good frame — that was exactly the one-shot full-tree generation this whole HTML-first pipeline exists to avoid, and it reliably produced a sparser result that overwrote/deleted what the reliable build had just drawn.) This comparison step is best-effort and never fails the overall generation if it errors out — the initial render already succeeded and stays on the canvas regardless.
  - A component instance is only ever dropped in with its own default sizing and adjusted through its own listed properties (toggling variants, setting text/icon values) — PromptPixel never resizes or overrides a component's width/height.
- Provider adapters for OpenAI, Anthropic, Gemini, and OpenRouter call their real APIs from the plugin's main thread, including multimodal (image) requests for the "vẽ lại theo ảnh" flow; `openai-compatible`/`custom` reuse the OpenAI-compatible request shape against a user-supplied Base URL. Use a vision-capable model (e.g. `gpt-4o`, a Claude 3+ model, `gemini-1.5-*`) when sending an image — a text-only model will error.
- A standard screen size (default 1366×768, configurable in Rules) is enforced on every generated screen — the root frame is always created at exactly that fixed width and height, regardless of what the AI proposes, and clips its content at that boundary (content that doesn't fit is cut off at the edge rather than spilling out past the configured screen size).
- Every generation always reports a plain node-count line in the Generate tab's warnings ("Bản vẽ có N node (X vùng layout, Y dòng text, Z component)") so it's immediately obvious how much content actually got built, and how many of the flat leaf elements didn't get mapped to a real component (shown as "N/M phần tử không map được component thật").
- `UIPlanNode` supports a third variant besides `componentId`/`layout`: a freeform `text` node, used only when no catalog component fits. Its `style` must reference a loaded Text Style (default `"Body Regular"`) — the AI can't invent arbitrary fonts/sizes. Likewise a `layout` container may set `fill` to a loaded Color Style for an on-brand background; omitted, it stays transparent.
- Text Styles and Color (Paint) Styles are registered the same way as components — scanning the library's source file also picks up its published text/paint styles (via their publish `key`, resolved cross-file with `figma.importStyleByKeyAsync`), shown per-library in the Libraries tab alongside the component list.
- Scanning a library also captures each component's real property definitions (name, type, and for VARIANT properties the exact allowed values) straight from Figma's `componentPropertyDefinitions`, and feeds that schema to the AI per-component — so it sets only properties/variant values that component actually supports, instead of guessing plausible-sounding generic names (a recurring failure mode before this was added).
- Curation is simple: whatever's in a library's loaded component list is fair game for the AI to use; delete a row to take it out of consideration. Components scanned from the library file are grouped in the UI by the page they were found on. Components found on a page named exactly "Icons" are also surfaced to the AI as a dedicated icon pool: when a component instance has an icon-swap (`INSTANCE_SWAP`) property, the AI can set it to one of these icon componentIds to pick a specific icon, or leave it unset to keep whatever icon the component defaults to. Name your icon components' page "Icons" in the library file for this to work.

### Library discovery limitation

Figma's plugin API only exposes `getAvailableLibraryVariableCollectionsAsync()` for discovering libraries — there is no public API to list every component library added to a file regardless of whether it publishes Variables. If a library only contains components/styles and publishes no Variable Collection, it will not appear when you click "Load libraries từ file hiện tại", even though it's genuinely enabled in the file. Publishing at least one Variable Collection from that library (even an empty design-token collection) makes it discoverable.

### Registering components/styles — no API browses a remote library's contents

Figma's plugin API also has no way to list the components or styles that live inside an already-enabled external library — plugins can only see nodes/styles physically present in the currently open file. Each library row in the Libraries tab has a "Nạp" ("load") action that bulk-scans everything published in the current file (components, component sets, text styles, paint styles), across every page, into that library's registry — it only finds anything when you have the actual library source file open (where those assets are defined and published from). Components whose name (or the last `/`-separated segment of it) starts with `_` are treated as private/internal and skipped during the scan. `clientStorage` (and so the whole registry) is shared across files by the same plugin install, so scanning once while the library file is open makes those assets usable later in any other working file, by key.

### Custom/OpenAI-compatible endpoint limitation

Figma requires every domain a plugin can `fetch()` to be listed statically in `manifest.json` → `networkAccess.allowedDomains`; there is no way to allow a domain at runtime. The manifest ships with the four fixed providers' domains (OpenAI, Anthropic, Gemini, OpenRouter) already allowed. If you use the `openai-compatible` or `custom` provider kind with your own Base URL, add that domain to `allowedDomains` yourself and reimport the plugin manifest — requests to any other domain will fail.

## Development

```bash
npm install
npm run build
```

Before importing the plugin into Figma, create a development plugin in Figma and replace the placeholder `id` in `manifest.json` with the generated numeric plugin ID. Then import `manifest.json` via **Plugins → Development → Import plugin from manifest**.

Useful commands:

```bash
npm run typecheck
npm run build
```

## MVP flow

1. Configure an AI provider with BYOK.
2. Load the libraries enabled in the current Figma file and choose which ones AI may use.
3. Add design rules in Markdown.
4. Ask PromptPixel to generate a screen from the Generate tab.
5. The request resolves against the enabled libraries' component catalogs — the AI can only reference components you've enabled.
6. Structure and content come from an HTML wireframe, parsed deterministically (not trusted to an AI-authored JSON tree — see the "Two fixed generation workflows" bullet above); only the leaf-to-component mapping step's response is validated against the enabled library allowlist, and any element that fails to map keeps a safe plain-text fallback instead of touching nothing.
7. Component keys are imported, instances created, properties applied, and Auto Layout built in the current Figma page. Per-node failures (e.g. a component removed from the library) are skipped with a warning instead of aborting the whole render.
